# 知识库文章日常发布与维护

本流程沿用文章仓库现有的 Vercel deploy hook。日常更新不需要创建网站同步 PR、
安装 GitHub App、配置跨仓写入令牌，或要求运营手动维护生成的 JSON。
本次自动化不修改页面 UI，也不自动生成译文、分类或 SEO 文案。

## 运营同学：正常发文只做这些

1. 在文章仓库新建或修改文章、图片、真实译文，提交 PR。
2. 查看 PR 检查结果并修复报告的问题；内容审核通过后合入文章仓库 `main`。
3. 等待网站自动构建完成。文章工作流通过只代表构建请求已发出，最终发布结果以
   Vercel 部署状态及线上内容版本为准。

新文章使用独立的小写目录，例如 `what_is_ckb/index.md`；词之间用单个下划线。
图片放在该文章的 `images/` 目录。中文译文与英文同目录，文件名为 `index_zh.md`。
英文 `index.md` 必须存在；没有准备好的译文不要创建占位文件。

文章头部继续使用现有字段，例如：

```yaml
---
title: 'Example article title'
subtitle: 'A short introduction to this article.'
coverImage: 'images/cover.png'
date: '2026-11-05T08:00:00.000Z'
author:
  - 'github:authorHandle'
---
```

日期必须是真实的 ISO 时间，带秒数及 `Z` 或明确时区。`draft`、`published` 如需使用，
必须写 YAML 布尔值 `true` / `false`，不能写成字符串 `'true'` / `'false'`。
可选 `description` 用于该语言的已审核 SEO 摘要；不填时沿用该语言已有摘要的回退规则，
不会自动调用 AI 编写描述，也不会把英文文案自动冒充译文。

网站在构建时自动生成和更新内容哈希、阅读时长、译文清单、文章元数据和 sitemap。
运营不需要运行生成脚本，不需要把 `metadata/catalog.json`、
`metadata/reconciliation.json` 的机械更新提交回文章仓库。
现有人工分类、精选顺序和推荐设置会保留；未分类的新文章仍可进入全部文章列表，
不会自动猜测其分类。

当前文章语言入口仅展示实际存在的英文／中文版本；其他已存语言不会因此自动出现在
切换入口中。文章之外的 KB 导航与主页仍为英文，自动化不调整这些 UI 规则。

已发布目录、文章文件及图片不要随意改名或删除。URL 迁移、撤稿及移除旧资源需要与
网站维护人协调重定向／兼容处理，不能当成普通内容更新直接发布。

未来日期只影响当前构建时的发布判断，**尚未提供定时唤醒构建**。到达日期时没有新构建，
文章不会凭空出现；预约发布需要维护人安排届时重建，不能仅凭填写未来日期视为完成。

## 自动化实际做什么

```text
文章 PR：可信网站校验器检查源文件，不接触部署密钥
    ↓ 内容审核、检查通过并合入 main
文章工作流：重新读取 main → 校验 → 请求现有 Vercel deploy hook
    ↓
网站构建：解析一次官方文章 main 的精确 SHA → 校验 → 生成元数据 → 构建
    ↓ 构建与发布成功
线上新版本（同时记录网站 SHA 与文章 SHA）
```

文章源文件校验使用网站仓库已审核的 `main` 分支工具，不从文章 PR 执行发布逻辑。
使用 deploy hook 的任务独立运行，不检出文章代码。权限仅为仓库内容只读，
不需要 GitHub Actions 写权限或跨仓写权限。

构建开始后锁定一个文章快照，不能在生成不同页面时各自获取最新内容。
构建失败不会替换当前线上成功版本。发送 hook 的 HTTP 请求成功也不等于网站已经上线。

## 网站维护人：构建模式和版本记录

| 配置 | 行为 | 适用场景 |
| --- | --- | --- |
| 未设置 `KB_CONTENT_SOURCE` | 使用网站提交中锁定的文章 gitlink（`pin`） | 默认本地开发、CI、Preview |
| `KB_CONTENT_SOURCE=main` | 构建开始时获取官方文章 `main`，锁定其精确 SHA | 正式项目日常自动发布 |
| `KB_ARTICLE_SHA=<完整 SHA>` | 使用已审核官方 `main` 历史中的指定兼容版本（`sha`） | 复现、故障恢复 |

`KB_ARTICLE_SHA` 仅接受小写、完整的 40 位十六进制提交 SHA，不接受分支名或短 SHA，
并优先于 `KB_CONTENT_SOURCE`。该版本仍需属于官方文章 `main` 历史，且不能早于当前
网站要求的兼容基线；不是任意旧版或未合入分支都能强行部署。

正式环境显式设置 `KB_CONTENT_SOURCE=main`，不要把它误配到所有 Preview／本地环境。
本地需要验证最新内容时应使用独立、干净的检出，避免替换本地尚未提交的文章修改。
脚本会拒绝覆盖脏的实时内容检出；不要通过强制清理用户文件来绕过保护。

现有 Vercel build command 可以继续先初始化 submodule 再运行网站构建：

```sh
git submodule sync -- public/education_hub_articles && git submodule update --init -- public/education_hub_articles && yarn build
```

不要把它改成任意时机的 `git submodule update --remote`。文章来源解析、版本记录和
元数据生成由网站构建脚本统一处理，网站仓库仍保留可审查的兼容基线 gitlink。

发布成功后访问：

```text
GET https://www.nervos.org/api/kb/release
```

接口只公开版本证据，不公开密钥；主要字段为：

| 字段 | 含义 |
| --- | --- |
| `websiteSHA` | 此次网站代码提交 |
| `articleSHA` | 此次实际构建使用的文章提交 |
| `articleBaselineSHA` | 网站提交要求的文章兼容基线 |
| `articleRepository` | 固定的官方文章仓库地址 |
| `contentSource` | `pin`、`main` 或 `sha` |
| `workingTree` | 是否包含本地未提交内容；正式部署应为 `false` |

接口使用不缓存响应。没有可用版本证据时返回 `503`，不要把它理解为自动使用了最新文章。
网站与文章 SHA 可能不同步变化：仅更新文章时，网站 SHA 可以保持不变，这是正常的。

## 管理员：首次启用顺序

必须先部署网站能力，再打开文章触发器。不要先改线上数据源或先触发文章部署。

1. 合并网站自动化 PR。保持默认 `pin` 构建，确认现有正式内容能正常构建、预览和发布。
2. 在正式 Vercel 项目的 **Production** 环境设置 `KB_CONTENT_SOURCE=main`；确认没有残留
   `KB_ARTICLE_SHA` 覆盖，然后创建并验收一次正式构建。
3. 访问 `/api/kb/release`，确认 `contentSource=main`、`workingTree=false`，文章 SHA 与预期
   的官方 `main` 一致，并抽查正文、图片、真实译文和 sitemap。
4. 确认文章仓库已有的 Actions secret `NERVOS_ORG_DEPLOYMENT_WEBHOOK` 仍指向正确的正式
   Vercel 项目。保留原密钥即可，不要把 URL 粘贴到 PR、文档、群聊或构建日志。
5. 网站正式部署确认后，再合并文章工作流 PR。该工作流在官方文章仓库**默认启用**，
   不需要新增管理员变量；这次合并本身就会校验文章 `main` 并请求正式构建。
   不要在网站新构建流程尚未上线时提前合并。
6. 确认文章校验任务通过、hook 接受请求、Vercel 实际部署成功，最后核对线上版本接口。
   从这时起，普通文章合入 `main` 才可视为接入了自动构建流程。
   如需重试，可从文章 `main` 手动运行 **Nervos Official Production Deployment**。
7. 建议管理员为文章 `main` 配置必需检查 `check-slugs`、`validate-content`，要求内容审核并
   限制直接推送。工作流文件本身不会自动建立这些保护。应额外审核 `.github/`、脚本和
   迁移规则变更，不能只审正文。启用所需规则前，先确认检查名在实际 PR 中正常出现；
   此项需管理员协调，不是这次代码接入的阻塞条件。即使文章 PR 未被保护规则拦截，
   网站每次构建仍会独立校验，未通过网站校验的内容不能替换正式成功版本。

此流程不需要新增 GitHub App、跨仓令牌或文章仓库启用变量。可选的文章 Actions variable
`KB_PUBLISHING_ENABLED` 设为 `false` 时暂停工作流；正常情况不设置。
若它此前已存在且为 `false`，需要管理员移除或修改该暂停值，也可以使用 Actions 原有的
停用／启用工作流功能。首次 Vercel 环境变量及分支保护仍需相应管理权限，不能声称代码
合并后这些设置自然就会生效。

## 失败处理和回滚

- PR 校验失败：按错误信息修正源文件，再提交到同一 PR；不要手工改生成的哈希绕过校验。
- main 校验失败：不调用 deploy hook；修正文章后重试，线上保留上一成功版本。
- hook 请求失败：检查现有密钥、项目与网络后，从文章 `main` 手动重跑工作流；不要公开
  secret 的值。HTTP 2xx 只表示构建请求被接受，仍需检查 Vercel 后续结果。
- Vercel 构建失败：检查网站构建日志及源文件校验，确认实际文章版本，不把 Actions 的绿色
  hook 任务当作正式上线成功。
- 有新的文章合入时触发多次构建：以最终正式域名实际返回的 `/api/kb/release` 为准，确认
  没有把已过时内容当作最新发布。

紧急恢复按下面顺序操作：

1. 先暂停文章自动发布：在 Actions 停用文章 **Nervos Official Production Deployment**
   工作流，或由管理员将可选变量 `KB_PUBLISHING_ENABLED` 设为 `false`；
   同时通知运营暂缓合并，检查并取消
   不应继续发布的在途构建。关闭变量不等于取消已经提交给 Vercel 的构建。
2. 在 Vercel 选择上一个已验收的**不可变部署产物**回滚正式域名，并验证其版本接口与
   实际页面。记录部署 ID、网站 SHA、文章 SHA。
3. 如果需要重新构建一个固定内容版本，在正式环境临时设置完整的 `KB_ARTICLE_SHA`，
   验证该版本符合兼容约束，再构建与验收。
4. 修复完成后，确认是否仍需保留固定 SHA；若恢复日常跟随，清除临时 `KB_ARTICLE_SHA`，
   验证 `KB_CONTENT_SOURCE=main` 的正式构建，再重新开启文章自动发布。

**不要仅重新部署一个旧网站提交就认定完成回滚。** 当生产环境仍为 `main` 模式时，
重建旧网站代码也会获取当时最新的文章内容，可能重现相同问题。优先使用已经生成的
不可变 Vercel 部署产物；恢复前先暂停自动发布，避免回滚版本被后续构建覆盖。

## 本轮明确不包含

- IndexNow 继续保持关闭，不能因为文章自动发布已接通就自动开启搜索引擎通知。
- Google／Bing 的站长平台权限、sitemap 提交和收录结果仍由对应负责人处理。
- 不自动生成分类、精选、译文或 SEO 文案；已有英文／中文入口规则和 UI 不变。
- 不把未来日期等同于定时发布；需要后续重建才会重新计算可发布内容。
- 不把历史内容的精确数量作为日常发文门槛，也不要求运营维护这些历史验收数字。
